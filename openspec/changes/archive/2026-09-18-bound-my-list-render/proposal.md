## Why

This change fixes **B1** from the 2026-09-12 memory note ("Unbounded My List render"), the last of that note's three causes still open.

**This reverses a recorded decision.** `docs/ISSUE_TRIAGE.md:435` records B1 as "Decided 2026-09-13: keeping as-is, not fixing | Removed from this doc", and `:230` repeats "B1 stays dropped". **No rationale for that call was recorded anywhere** — searched for at `docs/ISSUE_TRIAGE.md`, the resolved docs, and `git log -S"B1" -- docs/` (which returns nothing, the triage docs being gitignored). The decision is being reversed because the user re-reported the same slowness on 2026-09-18, with a second symptom — the in-page search feeling worse than the other filters — that traces to the same cause. Nothing found while re-verifying conflicts with any reason B1 might have been dropped for; the work is a few dozen frontend lines following a pattern four other pages already use.

The other two causes are already closed: **N4** (unprojected entries query) and **R5** (`SettleAsync`'s N+1 writes), both shipped in `my-list-dashboard-read-performance` (2026-09-14). This change is **frontend-only** and touches no backend file.

**Verified against the code** (2026-09-18, at `44606a7`). Paths without a prefix are under `frontend/src/`.

- **The render is unbounded.** `pages/MyListPage.tsx:578-642` (`renderBody`) maps over `derived.groups`/`derived.items` with no slicing anywhere. Every other long-list page bounds itself: `pages/SeriesBrowserPage.tsx:76,125,132`, `pages/SeasonPage.tsx:184,355`, `pages/YearPage.tsx:153,308` (`PAGE_SIZE = 24` each) and `pages/SearchPage.tsx:84,149` (`CHUNK_SIZE = 48`) all hold a `visibleCount` in `useRestorableState`, slice to it, and grow it from an `IntersectionObserver` sentinel. My list is the only one that does not.
- **Every row's image is requested at mount.** `components/RowPicture.tsx:32-39` renders a bare `<img>` with no `loading` attribute, so several hundred entries means several hundred concurrent requests to MAL's CDN on every visit to the page.
- **Typing pays the full-list cost per keystroke.** `query` (`:158`) updates on every keystroke and re-renders `MyListPage`, which re-runs `renderBody`'s `.map()` over the full unbounded arrays. `useDebouncedValue(query, 200)` (`:329`) only delays `derived` (`:451-498`) recomputing — it does not stop the map. `components/MyListRow.tsx` is `memo`-wrapped with stable `useCallback` props (confirmed correct; unchanged by this change), so no individual row re-renders, but React still walks and diffs every row's props each time. A filter click pays that cost once; an N-character query pays it N times. That is why search feels worse than the other filters even though the filtering itself is sub-millisecond.

## What Changes

- **One shared reveal budget for the whole page, not one per status group.** `PAGE_SIZE = 24` (matching `SeriesBrowserPage`/`SeasonPage`/`YearPage`; `SearchPage`'s 48 is for a card grid, not a row layout) and a single `const [visibleCount, setVisibleCount] = useRestorableState('visibleCount', PAGE_SIZE)`.
  - **Grouped mode:** walk `derived.groups` in its existing order with a running remaining-budget counter starting at `visibleCount`. Each group's header renders unconditionally with its true full count (`group.items.length`) — headers are text, not the expensive part. Each group's `<ul>` renders `group.items.slice(0, Math.min(group.items.length, remaining))` and decrements `remaining` by however many rows it actually drew, passing any leftover to the next group. A group that exhausts the budget draws a prefix and later groups draw zero rows for now, their headers still stating real counts; those rows appear on scroll, exactly as on the other four pages.
  - **Flat mode:** `derived.items.slice(0, visibleCount)`, the pattern already at `SeriesBrowserPage.tsx:132`.
  - **One sentinel `<div>`** after the last rendered row (page-wide, not per group), with an `IntersectionObserver` bumping `visibleCount` by `PAGE_SIZE` capped at `derived.shown` — the mechanism at `SeriesBrowserPage.tsx:119-130`.
- **The query debounce is removed.** `useDebouncedValue(query, 200)` (`:329`) is deleted and `derived` filters off raw `query`. Its only real job today is limiting how often the unbounded render runs, which the reveal cap now bounds independently. The hook itself stays — `hooks/useAnimeSearch.ts:36-37`, `SeasonPage.tsx:291` and `YearPage.tsx:246` still use it; only MyListPage's import and call go.
- **`visibleCount` resets to `PAGE_SIZE` whenever the result set or its order changes** — on any change to `query`, `statusFilters`, `typeFilter`, `airingFilter`, `scoreFilter`, `sort`, `sortDirection`, `sortThen`, `airingStatusFirst` or `groupByStatus` (`derived`'s own dependency list at `:486-498` minus `scopedItems`). **Not optional polish:** without it, removing the debounce reintroduces per-keystroke cost proportional to how far the user had already scrolled.

  This must be explicit here, unlike on the other four pages. Those route their filters and sort through `useSearchParams`, so each change mints a new history entry and `useRestorableState` reseeds under the new location key on its own (`hooks/useRestorableState.ts:16-23`; the comment at `SeasonPage.tsx:179-183` says so outright) — no code there resets `visibleCount` on purpose. MyListPage deliberately keeps these controls off the URL (`MyListPage.tsx:143-149`: recap scope is "the only use of useSearchParams on this page"), so each control is an independent `useRestorableState` call with no shared identity and that reseed never fires. The reset follows the codebase's existing idiom — a render-time comparison against a previous value, calling `setVisibleCount(PAGE_SIZE)` synchronously during render, as `hooks/usePageData.ts:62-66` and `hooks/useRestorableState.ts:20-23` both already do — not a `useEffect`.
- **`loading="lazy"` on `components/RowPicture.tsx`'s `<img>`.** A cheap backstop for whatever is mounted ahead of the visible area. Applied globally after checking all 27 call sites; see Impact.
- **No change to `components/MyListRow.tsx`** — already correctly memoized, confirmed during this triage.

## Capabilities

### New Capabilities

None. Nothing about what the list *contains* changes.

### Modified Capabilities

- `library-views`:
  - **Added:** "My list reveals its rows as the page scrolls" — an initial bounded set of rows renders and more are appended automatically on scroll, with **one budget shared across the status groups** (so a group's header still states its real count whether or not all its rows are drawn), and any change to the find-in-list text, a filter, the sort, the tiebreaker or the grouping choice resets the reveal to the first batch. Added rather than folded into an existing requirement because nothing existing changes — this is a new concern about *when* rows are drawn, not about which rows or in what order. Phrased after the precedent already in `navigation-and-search/spec.md:491` for `SearchPage`, but broader: that one resets on sort alone, this resets on every control. The same requirement carries the debounce removal, as "narrowing SHALL take effect as the user types, without an imposed delay".
  - **Not modified:** "My list grouped and ordered by status" (`spec.md:6`). Grouping, group order, and what each row shows are untouched.
  - **Not modified:** "Find in list" (`spec.md:237-260`) names no debounce timing, so removing the 200 ms delay contradicts nothing there. **Confirmed by re-reading**, not assumed.
  - **Not modified:** "My list reports what is being shown" (`:496`), "My list grouping is an explicit choice" (`:471`), "Consistent list placement across my-list view modes" (`:812`). The results line keeps reporting `derived.shown`/`derived.total` — matched and total counts, neither of them the drawn-row count — and headers keep their real counts.
  - **Not modified:** the "same scroll position" language in the recap-picker dismissal scenario (`:844`). `visibleCount` is a `useRestorableState` value like every other control on the page, so a restore brings back the same amount of list and the same offset lands on the same rows.
- `artwork-presentation`:
  - **Added:** "Row pictures are requested as they come into view" — the row picture slots let the browser defer a picture's request until it nears the viewport, using native lazy loading rather than any scroll tracking of the app's own. This is spec-level rather than incidental because it is observable: on a slow connection, pictures below the fold arrive as they are scrolled to.
  - **Not modified:** "Orientation is read from the picture, not fetched" (`spec.md:76`). It already defines the before-loaded state ("Until a picture's proportions are known, its slot SHALL render at the unchanged portrait size"), which is exactly what a deferred picture sits in for longer; the new requirement restates that it still holds. `useWidePicture`'s behaviour under deferral was checked in code — see Impact.
  - **Not modified:** "Which surfaces are row picture slots" (`:47`). The new requirement reuses that list rather than restating or changing it.

## Impact

- **Frontend** (under `frontend/src/`):
  - `pages/MyListPage.tsx`: a `PAGE_SIZE` const, `visibleCount` + `sentinelRef`, the render-time reset, the `IntersectionObserver` effect, slicing in `renderBody`'s two branches plus the sentinel element; the `useDebouncedValue` import and call removed and `derived`'s dependency changed from `debouncedQuery` to `query`.
  - `pages/MyListPage.css`: one `.my-list-page__sentinel { height: 1px; }` rule, copying `SeriesBrowserPage.css:160-162`.
  - `components/RowPicture.tsx`: one attribute.
  - `components/MyListRow.tsx`: **unchanged**.
- **Backend, API, database:** no change, no migration. N4 and R5 are already fixed; nothing here touches `Services/Entries/`, `Services/Library/MyListService.cs` or `Data/Repositories/UserAnimeEntryRepository.cs`.
- **`loading="lazy"` reaches every `RowPicture` call site** — 27 of them across `MyListRow`, `SearchBar`, `AiringTodayList`, `RankingOverlay`, `RankingSection`, `AnimeRankOverlay`, `EditHistoryOverlay`, `UnresolvedEpisodesOverlay`, `CompletionScoreOverlay`, `RelatedAnimeOverlay`, `RecapPage`, `ProfilePage`, `SettingsPage`, `AiringPage`, `TopAnimePage`. Each was checked for a path needing an eagerly-loaded image: there is none. `grep` for `html2canvas`, `toPng`, `domtoimage` and `screenshot` across `frontend/src` returns nothing, so no export or capture path depends on images being loaded. Every other site is an ordinary list, row or conditionally-mounted overlay, where a lazy image loads as soon as it intersects.
- **`useWidePicture` keeps working under lazy loading** — checked rather than assumed. `hooks/useLandscapePicture.ts:29-42` attaches a callback ref that takes `node.complete` when true and otherwise listens for `load`. A lazy image simply is not `complete` at attach time, so it takes the listener branch and the orientation flag flips when the picture arrives. That is already the cold-cache path today.
- **Risk this change accepts.** Per-keystroke filtering is now synchronous and unthrottled. It is bounded by `scopedItems.length` (a personal list, a few hundred entries) and by a render capped at `PAGE_SIZE` rows, so it is cheap at any realistic size — but a list an order of magnitude larger would make the `derived` filter+sort itself the cost the debounce used to hide. Virtualization (below) is the answer if that ever arrives.
- **The frontend has no test runner.** `frontend/package.json` has no test script and no test dependency (scripts are `dev`, `build`, `lint`, `preview`; devDeps are Vite, oxlint, TypeScript and types), and `frontend/src` contains no `*.test.*` or `*.spec.*` file. **The nine test cases in the request cannot be written as automated tests without first adding vitest + React Testing Library + jsdom**, which is a change of its own and is not proposed here. They are carried into `tasks.md` as an explicit manual walkthrough instead — item for item, none dropped — which is what this repo's frontend changes already do (see `archive/2026-09-11-redo-my-list-filtering-and-sorting/tasks.md` §7). Say the word and adding the test harness becomes a separate change.
- **Docs:** `docs/ISSUE_TRIAGE.md` (local, gitignored) — B1's row at `:435` moves from "keeping as-is, not fixing" to resolved, and the Phase 5 note at `:230` drops "(B1 stays dropped)".
- **Out of scope:**
  - Any backend change.
  - **Per-group reveal budgets** — considered and rejected. A viewport shows a handful of rows regardless of how many groups have content; 24 rows in each of 6 groups is up to 144 mounted rows, nearly all off-screen, for no visible benefit over one shared count. Reaching a later group means scrolling past every earlier group's real rows either way.
  - **Virtualization/windowing** (e.g. `react-window`) — would keep the DOM bounded even after scrolling the whole list, which scroll-triggered reveal does not. Not chosen: a new dependency, a bigger change, and inconsistent with how four other pages already solve this. Worth revisiting only if a list gets large enough that reveal alone stops being enough.
  - **Moving MyListPage's filters onto the URL** to inherit the other pages' free reset — a larger change; the explicit render-time reset gets the same result.
  - Adding a frontend test harness (above).
